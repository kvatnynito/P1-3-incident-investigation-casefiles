## Ruled Out / Do Not Re-check

These were investigated and closed this session. Do not re-investigate any of them without genuinely new evidence — re-checking a closed item wastes a session on ground already covered.

- **DNS/hostname resolution** — ruled out. RDP failed identically when connecting directly by IP (`10.10.10.100`), bypassing DNS entirely.
- **Wrong IP** — ruled out. `ipconfig` on `TEST-WIN10-LAN1` confirmed `10.10.10.100` matched what was being targeted.
- **Windows Firewall — simplified "Allowed apps" panel** — ruled out. Remote Desktop's Domain/Private/Public checkboxes were already all checked.
- **Windows Firewall — Advanced Security Inbound Rules** — ruled out. An initial "completely empty" result was the MMC console still loading, not a real gap; after refresh, RDP inbound rules (TCP-In/UDP-In) showed Profile: All, Enabled: Yes.
- **RDP-dependent services stopped** (Remote Desktop Configuration / Port Redirector) — starting them manually did not fix the issue on its own (see root cause below — this was actually part of the cause, just not sufficient by itself).
- **Proxmox VM-level firewall** — ruled out on both `TEST-WIN10-LAN1` and `AD-DC01`; the Firewall feature is disabled on both VMs.
- **Virtual NIC/bridge configuration** — ruled out on both VMs; both on `vmbr1`, no VLAN mismatch.
- **Network adapter connection state** — ruled out; adapter showed a normal connected icon, no disabled/unplugged indicator.
- **Enabling RDP inbound on `AD-DC01` (the source/client machine)** — ruled out as a fix; wrong direction, a source-side RDP setting doesn't affect an outbound connection attempt.
- **Ping/ICMP as a proxy for RDP (TCP 3389) connectivity** — ruled out, a red herring. Extensive ping cross-testing revealed an unrelated pattern: the domain controller (`AD-DC01`) accepts inbound ICMP Echo Request by default, member servers/workstations (`WEC01`, `TEST-WIN10-LAN1`) don't — a Windows default, not a bug, and not evidence about the RDP-specific failure.
- **WEC01 / TEST-WIN10-LAN1 domain membership** — verified, was never actually broken. Confirmed authoritatively via the System Properties "Domain:" field and the Computer Name/Domain Changes dialog on both machines. (Adapter-level DNS suffix settings are editable and are not proof of domain membership — don't treat them as such again.)

**Actual root cause (do not re-derive):** RDCS (Remote Desktop Configuration) and the Port Redirector service were manually force-started out of their normal boot dependency order. `TermService`'s RDP-Tcp network listener never properly bound to port 3389 as a result, even though every individual service showed "Running." A clean reboot of `TEST-WIN10-LAN1` fixed it by re-initializing all RDP services in correct dependency order.
